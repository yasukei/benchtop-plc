## Context

Milestone 6 moves from one program in one fixed cycle to a configured resource, as
IEC 61131-3 describes the software model: a configuration contains resources, a
resource contains tasks and program instances, and global variables are declared in
the configuration and the resource. Today a project has one configuration, one
resource, one cyclic task and one program instance bound to the first `PROGRAM`
(see `docs/project-format.md`). The compiler requires exactly one `PROGRAM` and
produces one `ProgramIR`. The runtime runs one scan loop with one interval. The I/O
image is 8 input and 8 output bits (`IoImage`, `setInput.bit`), and direct addresses
are BOOL only, on `PROGRAM` `VAR`. ADR 0010 left warm restart, acknowledge fault,
persisting `RETAIN` data and the start-up state after a reload for later.

The new features change the core types, the IR, the runtime, the UI–runtime protocol,
the project file and the monitor together. The implementation issues under
[#147](https://github.com/yasukei/benchtop-plc/issues/147) need one model.

As in ADR 0012, 0014 and 0015, the 4th edition text (IEC 61131-3:2025) was not
available when this ADR was written. Decisions that depend on the standard follow the
3rd edition text and secondary sources (vendor documentation for CODESYS, TwinCAT and
Siemens); they are not verified claims about 4th edition clauses. The checks and
project restrictions below are tracked in
[#92](https://github.com/yasukei/benchtop-plc/issues/92).

## Decision

### Configuration model

- A configuration is one project source, edited like a POU:

  ```
  CONFIGURATION Plant
    VAR_GLOBAL gSetpoint : INT := 50; END_VAR
    RESOURCE Station ON BENCHTOP
      TASK Fast (INTERVAL := T#10ms, PRIORITY := 1);
      TASK Slow (INTERVAL := T#100ms, PRIORITY := 5);
      PROGRAM Tank1 WITH Fast : TankControl;
      PROGRAM Tank2 WITH Fast : TankControl;
      PROGRAM Stats WITH Slow : Statistics;
    END_RESOURCE
  END_CONFIGURATION
  ```

  A project has at most one configuration source. It is listed after the data types
  and before the POUs, and saved as described under Project file. This matches the
  per-source editing model of ADR 0014 and ADR 0015.

- A configuration has exactly one resource (restriction). A second configuration or
  resource is a compile error. `ON` takes any identifier as the resource type and the
  compiler ignores it; TC6 v2.01 has no place for it, so only the source text keeps it.
  Text generated by benchtop-plc writes `ON BENCHTOP`.
- A project without a configuration source runs with an **implicit configuration**:
  one resource, one cyclic task and one instance of the project's only `PROGRAM`. The
  configuration, resource, task and instance names, the interval and the priority are
  the project fields that exist today (`Config`, `Res`, `Cyclic`, `mainInstance` in the
  bundled examples). The web app's cycle control sets the interval, as today. So
  existing projects keep running, and a configuration is something a user adds when
  they need it.
- Under the implicit configuration, zero or several `PROGRAM`s remain compile errors,
  as today; the diagnostic says that a configuration source is needed to run several
  programs. With a configuration source, a `PROGRAM` without an instance is compiled
  and checked but not run, and a resource without any program instance is a compile
  error.
- A program instance `PROGRAM Tank1 WITH Fast : TankControl;` has its own memory. A
  configuration may declare several instances of the same `PROGRAM` and instances of
  different `PROGRAM`s. Function and function block bodies stay in the IR once
  (ADR 0014); instances do not duplicate code.
- Every program instance needs `WITH` and one task (restriction). The configuration
  allows at most 16 tasks and 64 program instances (restriction), which bounds the
  monitor and telemetry.
- Instances of one task run in their declaration order in the resource.
- Names: the configuration, resource, task, program instance and global variable names
  share one case-insensitive namespace, which also excludes the ADR 0014 namespace
  (POU, data type and standard names). So `PROGRAM TON WITH Fast : Main;`, a task and a
  global both named `Alarm`, or a global named like a POU are compile errors.
- With a configuration source, task intervals come only from the source. The web app's
  cycle control is replaced by the per-task telemetry, and changing an interval means
  editing the source. `setCycle` is rejected while a configuration source is loaded.

### Tasks and scheduling

- A cyclic task: `TASK Fast (INTERVAL := T#10ms, PRIORITY := 1);`. An event task:
  `TASK OnAck (SINGLE := gAck, PRIORITY := 0);`, which runs once per rising edge of its
  input.
- Each task has exactly one of `INTERVAL` and `SINGLE`, and a `PRIORITY`
  (restriction; what the standard does with other combinations is listed under
  Restrictions). Parameters are written as `name := value` in any order.
- `INTERVAL` is a `TIME` or `LTIME` literal with a whole number of milliseconds from
  1 ms to 1 h (restriction). `T#10ms` is valid; `T#0.5ms`, `T#0s` and a variable are
  compile errors.
- `PRIORITY` is an integer literal from 0 to 65535, as the project file already
  allows. 0 is the highest priority, as in the 3rd edition.
- `SINGLE` names a non-constant `BOOL` global or a `%IX` address (restriction; no
  expressions, members or program variables).
- Scheduling is non-preemptive, which the 3rd edition allows: a running task is never
  interrupted. The runtime keeps a due time for each cyclic task (the first one is one
  interval after RUN starts) and samples event inputs:
  - The runtime ticks on the injected `Ticker` (ADR 0003) at the greatest common
    divisor of the cyclic intervals, or every 10 ms when there is no cyclic task.
  - Each tick starts a scheduler pass. A cyclic task is ready when its due time has
    been reached. An event task is ready when its input is TRUE now and was FALSE at
    the previous pass (the first pass after load or a restart compares with FALSE). A
    task that becomes ready during a pass waits for the next pass.
  - A pass runs its ready tasks one after another: highest priority first, then the
    task that has waited longest (earliest due time or edge), then declaration order.
  - After a cyclic task runs, its next due time is the previous due time plus one
    interval. If that time has already passed when the task finishes, the missed
    activations are not caught up: the due time moves forward by whole intervals until
    it is later than now, and each skipped activation counts as one **overrun**. A
    10 ms task due at 10 ms that finishes at 35 ms is next due at 40 ms, with two
    overruns (20 and 30 ms).
  - Example: with `Fast` at 10 ms and `Slow` at 30 ms, the runtime ticks every 10 ms;
    over 90 ms `Fast` runs 9 times and `Slow` 3 times, and at 30, 60 and 90 ms `Fast`
    runs before `Slow` when it has the higher priority.
- An overrun is counted and reported in the telemetry; it does not fault. A
  time-based watchdog stays deferred, as in ADR 0010.
- I/O image timing: before each task run, the runtime copies the current input image
  into the `%I` area; after each task run, it publishes the `%Q` area as the output
  image. Every task therefore sees fresh inputs, and because scheduling is
  non-preemptive, a task never sees a half-written image.
- The scan stages of `docs/runtime.md` become nested: image transfers stay at the task
  boundaries, and parameter transfers and forces surround each program instance. A
  task run is:
  1. copy the input image into the `%I` area;
  2. apply pending writes (they are consumed by the first task run that follows them);
  3. for each program instance of the task, in declaration order:
     1. copy its connected inputs in;
     2. apply every force;
     3. execute the instance;
     4. apply every force again;
     5. copy its connected outputs out;
     6. apply every force again;
  4. publish the `%Q` area as the output image.

  Forces are applied around every instance and after its output copies, not only
  around the task. A forced parameter wins over its connection (stages 2 and 4), and a
  forced destination wins over an output copy (stage 6), so no instance and no
  published image sees a value that an earlier step wrote to a forced variable. Inside
  one instance, ADR 0014's behavior is unchanged: a statement can read a value its own
  instance wrote to a forced variable earlier in the same run.

  Examples, with `A` (connected `Out => g`) running before `B` (connected `In := g`)
  in one task:
  - Without forces, `B.In` receives the value `A` produced in the same run.
  - With `A.Out` forced to TRUE while `A`'s body assigns FALSE, stage 4 restores TRUE
    before the copy, so `g` and `B.In` are TRUE.
  - With `g` forced to FALSE while `A` produces TRUE, the copy writes TRUE to `g`,
    stage 6 restores FALSE, and `B.In` receives FALSE.
  - With `gLamp AT %QX0.0 : BOOL` forced to FALSE and `A.Out => gLamp` producing
    TRUE, stage 6 restores FALSE, so `%QX0.0` is published as FALSE.

- Single scan (`step`) in STOP runs one pass in which every cyclic task runs once and
  every event task with a rising edge runs once, in the order above, regardless of due
  times.
- STOP, RUN, emergency stop and FAULT apply to the whole resource (ADR 0009, ADR 0010).
  A run-time error in any task faults the resource, stops every task and names the
  task, the program instance and the POU. STOP → RUN restarts the due times from the
  current time, so no overruns are counted for the time spent in STOP.
- ADR 0010's limit of 200,000 loop iterations counts per task run (ADR 0014 counted
  per scan; with one task this is the same).
- Telemetry per task: the number of runs, the last and the maximum execution time in
  milliseconds (measured with the injected `Clock`), and the number of overruns. Cold
  reset, warm restart and load clear it. The snapshot's scan count counts scheduler
  passes in which at least one task ran.

### Global variables

- `VAR_GLOBAL` sections are declared in the configuration (before `RESOURCE`) and in
  the resource (before the first `TASK`). Their globals are visible to every program
  instance of the resource. A resource global and a configuration global cannot share
  a name (restriction; no hiding).
- A `PROGRAM` or `FUNCTION_BLOCK` uses a global only through `VAR_EXTERNAL`:

  ```
  FUNCTION_BLOCK Pump
    VAR_EXTERNAL gSetpoint : INT; END_VAR
    VAR_EXTERNAL CONSTANT cMaxLevel : INT; END_VAR
  ```

  `VAR_EXTERNAL` in a `FUNCTION` is a compile error, as in the 3rd edition. An
  external without a matching global, a different type (using ADR 0015's exact-type
  rule, string lengths aside), and an initializer on an external are compile errors.
  An external aliases the global's storage, so the global's string length applies.

- A local variable may have the same name as a global; only a `VAR_EXTERNAL` brings a
  global into scope, and an external and a local of the same name in one POU are a
  duplicate declaration.
- Under the implicit configuration there are no globals, so every `VAR_EXTERNAL` is
  reported as an external without a matching global.
- Types: every type allowed in a `PROGRAM` `VAR`, including derived types, references
  and standard or user function block instances. A global instance is called through
  its external (`gTimer(IN := x, PT := T#1s);`), and ADR 0014's selection of timer and
  counter variants considers every binding in the project.
- `VAR_GLOBAL CONSTANT` requires `VAR_EXTERNAL CONSTANT`, and the other way round; a
  mismatch is a compile error. Global constants follow ADR 0014 and ADR 0015: the same
  types are allowed, they are folded at compile time, they get no `VariableId`, and
  assigning them is a compile error. Through `VAR_EXTERNAL CONSTANT` they count as
  constants wherever ADR 0013 requires one, including array bounds and `CASE` labels in
  that POU. A global constant's initializer may use global constants declared before
  it in the same configuration.
- Globals live as long as the resource, so `REF()` accepts an external and its elements
  and members. This extends ADR 0015's list of long-lived variables.
- Globals are initialized on load and cold reset, configuration globals first, then
  resource globals, each in declaration order, before any task runs.
- Direct addresses are allowed on globals (`gLevel AT %IW0 : INT;`), with the rules
  under Direct addresses.

### Program parameters

- `PROGRAM` `VAR_INPUT` and `VAR_OUTPUT` are allowed. `VAR_IN_OUT` in a `PROGRAM`
  stays a compile error (restriction), because a connection could not supply a
  variable of the exact type in every case.
- An instance declaration connects them:

  ```
  PROGRAM Tank1 WITH Fast : TankControl (Level := %IW0, Start := %IX0.0,
                                         Limit := 90, Pump => %QX0.0, Hours => gHours1);
  ```

- What a parameter can connect to, as in the 3rd edition's grammar:
  - an input (`:=`): a constant, an enumerated value, a global or a direct address;
  - an output (`=>`): a non-constant global, or a `%Q` or `%M` address.
- Types: a global or constant connected to an input follows ADR 0013 as for a function
  block input (implicit widening only); a global connected to an output follows the
  implicit conversions of an assignment. A direct address connected to a parameter
  acts as if the parameter were declared `AT` that address, so the size must bind the
  parameter's type (see Direct addresses): `%IW0` connects to an `INT`, `UINT` or
  `WORD` input.
- Inputs are copied in immediately before the instance runs, and outputs are copied
  out immediately after it, in the order given under Tasks and scheduling, so a later
  instance in the same task sees the outputs of an earlier one through globals. An
  unconnected input keeps its value between runs (its initial value, or a value
  written from the monitor); an unconnected output is not copied anywhere. Under the
  implicit configuration every parameter is unconnected.
- An unknown parameter, a type mismatch, an input connected with `=>` or an output with
  `:=`, an output connected to a constant, a constant global or an `%I` address, and a
  parameter connected twice are compile errors.
- Forces apply to the parameter at the force stages around its instance, so a forced
  input is not overwritten by its connection, a forced output is copied out with the
  forced value, and a forced global or address connected to an output keeps its
  forced value after the copy. A connected input rejects monitor writes, as an
  input-mapped variable does today, because the next copy would overwrite them; it
  accepts forces.

### Direct addresses

- Areas: `%I` (inputs) and `%Q` (outputs) have 64 bytes each, `%M` (memory) has 1,024
  bytes (restriction).
- Sizes and the types they bind (restriction: no `TIME`, date, character, string or
  derived types except aliases of these types):

  | Size | Bytes | Types                             | Example  |
  | ---- | ----- | --------------------------------- | -------- |
  | `X`  | 1 bit | `BOOL`                            | `%IX3.5` |
  | `B`  | 1     | `BYTE`, `SINT`, `USINT`           | `%QB2`   |
  | `W`  | 2     | `WORD`, `INT`, `UINT`             | `%IW0`   |
  | `D`  | 4     | `DWORD`, `DINT`, `UDINT`, `REAL`  | `%MD10`  |
  | `L`  | 8     | `LWORD`, `LINT`, `ULINT`, `LREAL` | `%ML1`   |

- Numbering counts in units of the size, as in CODESYS: `%IBn` is byte n, `%IWn`
  covers bytes 2n and 2n+1, `%IDn` bytes 4n to 4n+3, `%ILn` bytes 8n to 8n+7, and
  `%IXn.m` is bit m (0–7) of byte n. So `%IW0` and `%IW1` never overlap. Siemens and
  TwinCAT count `%IWn` from byte n instead; the 3rd edition leaves this to the
  implementation.
- Byte order is little-endian, as in CODESYS on common hardware: the lowest byte holds
  the least significant bits. So `%IX0.0` is bit 0 of `%IW0`, `%IX1.7` is bit 15 of
  `%IW0`, and `%IB1` is the high byte of `%IW0`. `REAL` and `LREAL` are IEEE 754
  binary32 and binary64 in the same order.
- The existing `%IX0.0`–`%IX0.7` and `%QX0.0`–`%QX0.7` keep their meaning.
- An address outside its area, a type the size does not bind, a hierarchical address
  (`%IX1.2.3`) and a partly specified address (`%I*`) are compile errors.
- Areas are memory, and a located variable is a view of its bytes: reading it reads
  the bytes, writing it writes them. Overlapping variables therefore always agree:
  after `%MW0 := 16#0102`, `%MB0` is 2 and `%MB1` is 1. Two variables that write
  overlapping `%Q` bytes (located variables or output connections) produce a compiler
  warning; overlaps in `%I` and `%M` are normal and produce none.
- A `REAL` or `LREAL` view can hold a bit pattern that is not a finite number, written
  through an overlapping view (`bits AT %MD0 : DWORD` beside `sample AT %MD0 : REAL`,
  then `bits := 16#7FC00000`) or through `setInput` with a `DWORD` value on an input
  read as `REAL`. ADR 0010 keeps such values out of variables, so the bytes are
  checked when the view is decoded:
  - A program read of the view, including the copy of a connected input, faults with
    `runtime.invalid-value` at the reading expression or the instance declaration.
    `x := sample;` in the example above faults.
  - Snapshots never decode it to a number: the leaf is reported as a new
    `VariableSnapshot` variant `{ kind: "invalidReal"; bits: string }` with the raw
    pattern (`"16#7FC00000"`). The monitor shows it as invalid with those bits, and a
    numeric display shows it as invalid. Neither faults nor throws in the host.
  - The bytes themselves are accepted: storing them, `setInput` and writes through
    other views never fault. Writing or forcing a finite value through the `REAL` view
    replaces them.
- `AT` is allowed on `PROGRAM` `VAR` and on `VAR_GLOBAL`. It stays a compile error in
  function blocks and functions (ADR 0014), in `VAR_TEMP`, with `CONSTANT`, and with
  `RETAIN` or `NON_RETAIN` (restriction).
- Load, cold reset and warm restart set the whole `%M` area to zero and then apply the
  initializers of `%M` variables in declaration order (configuration globals, resource
  globals, then each instance in declaration order). `%M` is never retentive
  (restriction). Variables located in `%I` and `%Q` follow the rules that
  `docs/runtime.md` states today for input-mapped and output-mapped variables: `%I`
  variables reject monitor writes and accept forces, and outputs stay OFF (zero) in
  every state except RUN and whenever the emergency stop is active, for the whole
  `%Q` area.
- Protocol: the input and output images become arrays of 64 byte values (0–255)
  in snapshots. `setInput` carries an address and a typed value, for example
  `{ address: "%IW0", value: { dataType: "INT", value: -5 } }`; the value's type must
  be one the size binds, and the runtime stores its bit pattern. `%M` is not part of
  the image; variables located there are monitored like other variables.
- The I/O image view shows the addresses that the program or the panel uses, in the
  type of their declaration, instead of all 128 bytes.
- Panel parts:
  - The existing bit parts accept any bit address in their area (`%IX0.0`–`%IX63.7`
    for inputs, `%QX0.0`–`%QX63.7` for lamps).
  - A numeric input binds to a `%IB`, `%IW`, `%ID` or `%IL` address with one of the
    types the size binds. It is a number field, with a slider when a minimum and a
    maximum are given; a value outside the type is rejected.
  - A numeric display binds to a `%QB`, `%QW`, `%QD` or `%QL` address with one of the
    types the size binds, and shows the value formatted as the monitor does, with an
    optional label.

### Retentive variables and restarts

- `RETAIN` and `NON_RETAIN` qualify `VAR`, `VAR_INPUT` and `VAR_OUTPUT` sections of a
  `PROGRAM` or `FUNCTION_BLOCK`, and `VAR_GLOBAL` sections, for example
  `VAR RETAIN hours : UDINT; END_VAR`. Both on one section, either one on
  `VAR_TEMP`, `VAR_IN_OUT` or `VAR_EXTERNAL`, either one in a `FUNCTION`, and either
  one with `CONSTANT` or with `AT` are compile errors.
- Unqualified variables behave as `NON_RETAIN` (ADR 0010).
- A function block instance or a composite variable in a qualified section passes the
  qualifier to its unqualified members and leaves. A member declared in its own
  `RETAIN` or `NON_RETAIN` section keeps that qualifier. So with
  `VAR RETAIN m : Pump; END_VAR`, `m`'s unqualified members are retained and its
  `NON_RETAIN` members are not; a `RETAIN` member of a `Pump` instance declared in an
  unqualified section is retained.
- A retained counter (`CTU`, `CTD`, `CTUD` and their variants), edge detector
  (`R_TRIG`, `F_TRIG`) or bistable (`SR`, `RS`) keeps its ports and its private state:
  the previous `CU` and `CD` of a counter, and the previous `CLK` of an edge detector,
  including whether it has been called yet. So a `CTU` with `CU` held TRUE and
  `CV = 1` still has `CV = 1` after a warm restart or a reload and the next call,
  because `CU` did not rise.
- Timers (`TON`, `TOF`, `TP` and their variants) are initialized by every warm restart
  and reload, even in a retained section (restriction): their start time refers to a
  clock that does not survive a reload. A `TON` whose `IN` is TRUE after the restart
  sees a rising edge at its next call and times again from there.
- References are never retained; they become `NULL` (restriction), because their
  targets are not guaranteed to exist after a restore.
- **Warm restart** is a new command, allowed in every state, including while the
  emergency stop is active. It initializes every variable that is not retained (and
  the `%M` area), keeps retained ones, clears a pending fault, clears forces and
  pending writes, and goes to STOP. It never goes to RUN. In FAULT it is the
  acknowledge-fault command that ADR 0010 asked for; there is one command, and the web
  app presents it as "Acknowledge fault" while the PLC is in FAULT. benchtop-plc has
  no fault history yet, so there is nothing for it to keep.
- Rows added to the state table of ADR 0010:

  | From | Event        | To   | Variables                                          |
  | ---- | ------------ | ---- | -------------------------------------------------- |
  | any  | warm restart | STOP | `RETAIN` kept, the rest initialized; fault cleared |
  | any  | page reload  | STOP | as warm restart, with `RETAIN` values restored     |

  The other rows do not change. In particular, cold reset and loading a program
  initialize `RETAIN` variables too, as ADR 0010 says. Applying an edited program or
  opening a project file is a load. This matches the CODESYS default, where a download
  reinitializes `RETAIN` variables.

- Keeping retentive values in the browser:
  - A stored set has two kinds of records: a leaf record (path, data type, value) for
    each retained scalar leaf, and a block record for each retained counter, edge
    detector or bistable, with its path, its exact block type including the variant
    (`CTU_DINT`), its ports and its private state as listed above. Timers have no
    records.
  - The Worker host sends all records, as one complete set rather than only the changed
    ones, to the page at most once per second while any of them changes, and after
    every command that changes the state. The page replaces the stored set with the
    latest one in the autosave record, so each stored set restores on its own. A reload
    can therefore lose up to about one second of changes (restriction); the page
    cannot wait for the Worker while it is being unloaded.
  - A page reload counts as a power loss followed by a warm restart: the app compiles
    the autosaved sources, loads them (which initializes everything), restores the
    stored retained values and stays in STOP. It never starts in RUN automatically, so
    an accidental reload cannot switch outputs on.
  - Records are matched to the loaded program by path (case-insensitive). A leaf
    record is restored only if the leaf exists, has the same data type and is retained
    in the loaded program; a string longer than the leaf's length is truncated as
    ADR 0015 stores do. A block record is restored, ports and private state together,
    only if a retained standard block with the same exact type exists at that path;
    otherwise the whole block keeps its initial state. Every other retained leaf and
    block keeps its initial value, and the app tells the user how many were not
    restored and which paths. This matters because autosave keeps source text that
    may not have been applied.
  - If the autosaved sources do not compile, the stored values stay in storage until a
    program loads. Storage that is unavailable or full produces a warning; the PLC
    keeps running.
- Rows added to the run-time error table of ADR 0010:

  | Condition                                                              | Reaction                                  |
  | ---------------------------------------------------------------------- | ----------------------------------------- |
  | Cyclic task activation missed (overrun)                                | Counted in the task's telemetry, no fault |
  | Stored retained value missing or not matching on reload                | Initial value, user told, no fault        |
  | Retained values cannot be stored in the browser                        | Warning, no fault                         |
  | Program read of a `REAL`/`LREAL` view holding a non-finite bit pattern | FAULT `runtime.invalid-value`             |

### Monitoring and protocol

- Variable paths are qualified by program instance (`Tank1.LEVEL`, `Tank1.PUMP1.RUNNING`,
  `Tank2.T[2]`), and globals are named by their own name (`gSetpoint`). Instance and
  global names cannot clash, so paths are unique. Paths are qualified under the
  implicit configuration too (`mainInstance.LAMP`), so they do not change when a
  configuration source is added (breaking change in the monitor and the changelog).
- The monitor groups variables under one collapsible row per program instance and one
  row for globals; inside a group, rows show the path relative to the group.
- Writes and forces address leaves by `VariableId`, as today, including globals and
  program parameters, with the restrictions above for `%I` variables and connected
  inputs. Constant globals have no `VariableId`.
- Inline values in a `PROGRAM` editor show the first instance of that `PROGRAM` in
  resource declaration order, from its last run, and the editor names that instance.
  A `PROGRAM` without an instance shows none. Choosing another instance belongs to
  debugging (Milestone 8).
- The snapshot carries the per-task telemetry. Annotations are keyed by POU as well as
  by line, since several `PROGRAM`s can run.

### IR

- The compiler's result becomes a resource: its globals, tasks and program instances,
  with each instance referring to its `PROGRAM` body and owning its storage, and one
  flat variable table over globals and all instances (ADR 0014, ADR 0015). Function,
  function block and `PROGRAM` bodies appear once. The exact shape belongs to #149.

### Project file

- The implicit configuration is written as today: one `configuration`, `resource`,
  `task` and, with a `PROGRAM`, one `pouInstance`. A 0.5.0 file therefore opens as a
  project without a configuration source, with its names, interval and priority, and
  saves back unchanged.
- A configuration source is written as TC6 v2.01
  `instances/configurations/configuration/resource`, with:
  - one `task` per task, with `name`, `priority`, and `interval` as an ISO 8601
    duration (`PT0.01S`) or `single` with the input's text (`gAck`, `%IX0.1`);
  - one `pouInstance` (`name`, `typeName`) per program instance, inside its task;
  - `globalVars` in the configuration and the resource, with the `constant`, `retain`
    and `nonretain` attributes, and variables mapped as `localVars` are today (name,
    type, address, initial value);
  - the exact source text in the benchtop-plc source extension inside the
    configuration's `addData`, as for POUs and data types.
- TC6 v2.01 has no element for program parameter connections, so they exist only in the
  source text; other tools see unconnected instances (restriction).
- On open, a configuration with the source extension uses that text, checked against
  the TC6 structure like a POU source (`project.stale-source` when they disagree). A
  configuration without it opens as the implicit configuration only when the implicit
  configuration can represent it: exactly one task, which has an `interval` and no
  `single`, at most one `pouInstance`, and no `globalVars`. Anything else becomes a
  configuration source generated from the structure, as `joinProgram` does for POUs.
  So a file with only `<task name="OnAck" single="%IX0.1" priority="0">` and one
  instance opens with a generated source containing
  `TASK OnAck (SINGLE := %IX0.1, PRIORITY := 0);`, and its program still runs only
  on rising edges.
- POUs gain `externalVars`, and `localVars`, `inputVars`, `outputVars` gain the
  `retain` and `nonretain` attributes. Addresses keep the `address` attribute, now with
  every size and area.
- Several configurations or resources, a `pouInstance` directly in a resource (a
  program without a task), `accessVars` and `configVars` are rejected on open
  (restriction).
- Saving requires the configuration source to parse and its initializers to pass the
  ADR 0014 checks; its semantic errors are kept for the compiler, as for POUs.

### Names

- `CONFIGURATION`, `END_CONFIGURATION`, `RESOURCE`, `END_RESOURCE`, `ON`, `TASK`,
  `WITH`, `VAR_GLOBAL`, `VAR_EXTERNAL`, `VAR_ACCESS`, `VAR_CONFIG`, `RETAIN` and
  `NON_RETAIN` are already reserved, so no new keyword is added. `INTERVAL`, `SINGLE`
  and `PRIORITY` are recognized only as task parameter names and stay usable as
  identifiers (see Restrictions).

### Restrictions and points to check

The following decisions are based on the 3rd edition and need verification against the
4th edition text:

- The configuration syntax: `CONFIGURATION`, `RESOURCE ... ON`, `TASK`,
  `PROGRAM ... WITH ...`, with `VAR_GLOBAL` in the configuration and the resource.
- Program connections take a constant, enumerated value, global or direct address as an
  input source, and a global or direct address as an output sink.
- Task priority 0 is the highest; non-preemptive scheduling runs the highest-priority
  ready task, then the one that has waited longest; `SINGLE` schedules a task once per
  rising edge.
- What the standard does with a program without a task, a task with both `SINGLE` and
  `INTERVAL`, and a task without `PRIORITY`.
- Whether `INTERVAL`, `SINGLE` and `PRIORITY` are keywords.
- `VAR_EXTERNAL` is allowed in `PROGRAM` and `FUNCTION_BLOCK`, not in `FUNCTION`; its
  type and `CONSTANT` must match the global.
- `RETAIN` and `NON_RETAIN` are allowed on `VAR`, `VAR_INPUT`, `VAR_OUTPUT` and
  `VAR_GLOBAL`, not on `VAR_IN_OUT`, `VAR_EXTERNAL` or `VAR_TEMP`; how a qualifier on a
  function block instance combines with its members' own qualifiers.
- Warm restart keeps `RETAIN` and initializes `NON_RETAIN`; cold restart initializes
  everything. Unqualified variables are implementation-dependent (here `NON_RETAIN`,
  ADR 0010).
- Direct address syntax with `X`, `B`, `W`, `D` and `L` sizes and `I`, `Q` and `M`
  areas; the mapping of sizes to bytes and the byte order are implementation-dependent.

The following are benchtop-plc restrictions or choices, not claims that the standard
forbids other behavior:

- At most one configuration source with exactly one resource; the resource type after
  `ON` is ignored; projects without a configuration source run an implicit one.
- Every program instance needs `WITH`; at most 16 tasks and 64 instances.
- A task has exactly one of `INTERVAL` and `SINGLE`, and a `PRIORITY`; `INTERVAL` is a
  literal of whole milliseconds from 1 ms to 1 h; `SINGLE` names a `BOOL` global or a
  `%IX` address.
- The runtime ticks at the greatest common divisor of the intervals; a pass runs the
  tasks ready at its start; missed activations are skipped and counted as overruns,
  which do not fault.
- Inputs are read before and outputs published after each task run; single scan runs
  every cyclic task once.
- Configuration and resource globals cannot share a name.
- `PROGRAM` `VAR_IN_OUT` stays rejected; a direct address connected to a parameter acts
  like `AT`; connected inputs reject monitor writes.
- Address areas of 64, 64 and 1,024 bytes; numbering in units of the size;
  little-endian byte order; located variables limited to the types in the table;
  overlapping `%Q` writers produce a warning.
- `AT` cannot be combined with `RETAIN`, `NON_RETAIN` or `CONSTANT`; `%M` is never
  retentive.
- References are never retained; timers are initialized by every warm restart and
  reload; retained counters, edge detectors and bistables keep their private state,
  stored as block records matched by path and exact block type.
- A `REAL` or `LREAL` view whose bytes are not a finite number faults when the program
  reads it and is shown as invalid in the monitor.
- One warm restart command, which is also the acknowledge-fault command.
- A page reload is a power loss followed by a warm restart into STOP; retained values
  are stored at most once per second; loading a program initializes `RETAIN` variables.
- Monitor paths are always qualified by instance; inline values show the first
  instance.
- Program parameter connections exist only in the source text of the project file;
  `pouInstance` in a resource, `accessVars` and `configVars` are rejected.

Issue #92 records each item. If a decision changes, the corresponding item there must
change with it. This ADR does not update `docs/compliance.md`: each implementing
sub-issue records its matching items there as Partial support or as a restriction when
the feature is implemented.

### Deferred scope

This ADR does not introduce several configurations or resources, `VAR_ACCESS`,
`VAR_CONFIG`, partly specified addresses (`%I*`), function block instances associated
with tasks (`FB1 WITH Slow` in a program configuration), preemptive scheduling, online
change, a time-based watchdog, fault history, `PERSISTENT` or IEC 61131-5 communication
function blocks. Classes and namespaces belong to Milestone 7, and selecting an instance
for inline values and breakpoints belongs to Milestone 8.

## Consequences

- Existing projects keep running without a configuration source, and a user who needs
  several programs adds one source. The cost is two ways to describe a task: the
  project fields for the implicit configuration, and the source text.
- Qualified paths change every monitor path once, including the bundled examples and
  their tests, but they never change again when a configuration is added.
- Non-preemptive scheduling on one tick keeps the runtime single-threaded and
  deterministic under the virtual clock, so conformance traces can check task ratios
  and priorities exactly. A long low-priority task delays higher-priority ones, which
  the overrun counter makes visible.
- Treating areas as memory gives overlapping variables one consistent value and lets
  programs share `%M` data, at the cost of replacing the 8-bit image in the protocol
  and every consumer.
- Persisting retained values from the Worker at most once per second keeps storage
  writes cheap but can lose the last second of changes on a reload.
- Implementation and conformance tests belong to the remaining sub-issues of #147.
  Accepting this ADR records the design; it does not make these features available in
  the app.
